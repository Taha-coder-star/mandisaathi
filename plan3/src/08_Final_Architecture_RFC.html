1. Final architecture summary

MandiSaathi is a modular monolith: one Python codebase, one container image, three process roles: web (receives webhooks), worker (runs conversation turns) and batch (daily data and model runs). It sits on one Postgres database (prices, forecasts, conversation state, job queue, logs). WhatsApp Cloud API (direct) is the only user interface.

  1. Ack fast. Every inbound webhook is verified, stored idempotently and acknowledged within about 1 s. All work happens in per-farmer serialised jobs.
  2. Voice joins text. A voice note gets one extra step (pre-checks + STT) inside the turn, then the same pipeline.
  3. Parse, then one LLM turn only if needed. A rule-based parser handles clean messages; a single LLM turn with intent-scoped deterministic tools handles the rest (≤ 3 tool iterations).
  4. Numbers come from tables, not from the turn. F1 and F3 are precomputed by the batch role with the same package used in the evaluation; F2 is a deterministic function over stored forecasts and cached distances.
  5. Template-rendered facts. Every rate, range, rupee amount, mandi name and date in a reply is rendered by a template from the tool payload. The LLM writes only a short framing sentence. A validator blocks any number-like token in the LLM text.

What we deliberately don't use: microservices, a vector database, an agent framework, a message broker, Redis, an object store, multi-tenant RLS, carousels, a farmer web app. None is justified by files 01–07.

3. Farmer data flow (text)

  1. [sync, C1] Meta POSTs → verify signature → INSERT inbound_event ON CONFLICT (wamid) DO NOTHING → if new, insert job(user_key) → 200. Target < 300 ms.
  2. [async, C2→C3] Worker claims the job, takes the farmer lock, loads all unprocessed messages of that farmer in timestamp order.
  3. [C3] Mark read + typing indicator. First contact without consent → consent message, stop. STOP → C14.
  4. [C6] Rule-based parse → patch. If intent and all required slots are resolved → skip the LLM.
  5. [C5, LLM call] Otherwise: context = state snapshot + last answer positions + last ~6 messages; LLM returns tool calls (update_query, price_now, get_forecast, best_mandis, get_outlook, set_alert…).
  6. [C6/C7] Normalise raw spans → merge state → gate (required slots present? no AMBIGUOUS slot?) → if not, clarification_needed{slot, candidates}.
  7. [C8/C9/C10] Deterministic lookup or ranking → payload (facts, run_id, positions).
  8. [C5, same turn] LLM writes at most one framing sentence. [C11] Validate → render facts by template.
  9. [C12] Send; store reply WAMID → answer_shown (positions, run_id) → commit.
  10. [async, C1/C12] Status webhooks update outbound rows (sent < delivered < read; failed terminal).

4. Voice data flow

  1. [sync, C1] Same as text; event type audio.
  2. [C3→C4, inside the turn] Download (5-min URL, re-query on expiry) → pre-checks (< 1 s ask again; > 120 s truncate and say so; silence → ask again, no STT call).
  3. [C4] STT primary with gazetteer keyterms → sanity checks → on failure fallback → both fail → "likh kar bhej dein" + alert.
  4. Native transcript + modality=voice + stt_meta → same flow from step 4. Only difference: voice-sourced crop/place/quantity that are non-exact or implausible trigger an echo-confirm before any tool answer [LANG §6].
  5. Audio deleted after transcription [OPS §3].

5. Daily batch flow (C13)

06:00 PKT  for each source loader: fetch/receive → save raw (sha256) → parse → price_obs (outlier_flag)
           → data_health row (rows, rejects, latest market_date)
           if any core source failed → keep yesterday's run as "current", flag stale, alert team
07:30      features (rules T1–T8) → F1 score all eligible series, h = 1..7 → forecast(run_id)
           series_coverage refresh
1st of month  F3 score → outlook(run_id)
09:30      C14: evaluate thresholds and digests on the new run → send (template if outside window)
Weekly     retrain F1 only in development branches; production uses frozen models until ps_v2

Times are ASSUMPTION until the sources' publish times are known (R3). The bot never computes a forecast inline.

6. Where-to-sell flow (deterministic, no LLM inside)

query_state ──► gate: crop covered? origin resolved (place or pin)? quantity + unit known?
        │ no → clarification_needed (LLM phrases one question; buttons by C11)
        ▼ yes
candidates: eligible mandis for crop within 150 km road distance (distance cache; OSRM on miss)
        ▼
for each m: P̂ = today's F1 P50 at arrival day; Net(m) = Q·P̂·(1−c) − T(d,Q) − F − Q·P̂·δ·ℓ
        ▼
risk rule: non-nearest m kept only if Net with its P10 > Net(nearest) with P50
        ▼
payload: top-3 {mandi, range, net, gain_vs_nearest} + cost assumptions + run_id ──► template ──► reply

7. Alert flow

  1. Farmer asks → C5/C6 extract {crop, mandi, direction, price} → C11 confirmation with [Haan] [Nahi] → C14 stores subscription (armed).
  2. After each daily run: crossings evaluated on non-SUSPECT prices; hysteresis 3%; caps (1/subscription/day, 3/farmer/day); budget cap.
  3. C12: inside window → service message; outside → approved template. Delivery status logged.

11. Data and licence boundary

  • AMIS: fetched only under the fetch policy (rules 1–12); raw pages never redistributed; source acknowledged in replies and reports.
  • Zarai Mandi: used only as provided by the co-supervisor and only within the written permission; no scraping of its site or app.
  • Synthetic data (FYP-I): labelled "Demo data (synthetic)" in every reply, chart and table; never presented as market data.
  • Replies show the source of the rate they quote; forecasts say "MandiSaathi andaza".

12. Security and privacy boundary

  • Inbound authentication: signature verification mandatory; invalid → 401, never processed.
  • Prompt injection: tools are chosen in code by intent; no tool writes anything except the farmer's own query state and subscriptions; there are no admin tools on the WhatsApp path.
  • Admin actions only via the server (SSH) or the read-only admin view; no WhatsApp admin commands in FYP-I.
  • Secrets in env / server secret file only; gitleaks in CI; LLM/STT accounts without cards in FYP-I.
  • Privacy per [OPS §3]: encrypted + hashed numbers, masked prompts, 90-day log retention, STOP deletes.

14. Scale (sized for an FYP, not a company)

  • Expected load: ≤ 50 active users, ≤ 1 message/s peak. One VM, 2 worker threads. The binding constraint is free-tier LLM/STT rate limits, not the database.
  • Batch: ≈ 3 crops × ≈ 40 mandis × 7 horizons ≈ 840 forecast rows/day: seconds on CPU.
  • Scale-up path (only on a measured trigger): more worker threads; paid LLM tier; nothing else.
